# Sales Invoice Lookup Inventory

Date checked: 2026-09-19

This inventory is based on the live MSSQL schema and lookup data, plus the current Sales Invoice API. It records lookup readiness only; it does not claim that posting or accounting journals are implemented.

## Result

All core tables required to populate the Sales Invoice form exist. The current API exposes the invoice type, item type, tax, unit, location, exchange-rate, customer, and salesperson lookups.

The API still needs invoice-specific endpoints for numbering rules, eligible contracts, eligible vehicles, and safe sales-account defaults before the UI should be considered complete.

## Live Configuration Confirmed

| Configuration | Result |
| --- | --- |
| Invoice voucher types | Five configured: Rental (31), Salik (32), Fine (33), Misc (34), Vehicle (38). |
| Numbering rules | Four date-range rules exist: Rental `RI`, Salik `SA`, Fine `FN`, Misc `MS`; six-digit numeric part with zero padding. Vehicle has no `tbl_SuffixPrefix` row. |
| Voucher tax mappings | Five mappings exist, one for each invoice type, all pointing to `taxId = 2`. |
| Item types | 23 type-specific item-type rows exist across the five invoice types. |
| Tax records | Two tax records exist. The applicable tax must still be filtered by `tbl_VoucherTypeTax`, not merely by `tbl_Tax.isActive`. |
| Units | Two unit records exist. |
| Currency and exchange rates | 47 currencies and one exchange-rate record exist. |
| Financial year | `tbl_FinancialYear` exists and is used to validate the invoice date. |

## Required Cascading Behavior

These cascades must be implemented in the UI and revalidated by the API. They are business dependencies, not database cascade constraints.

| Change | UI must refresh or clear | API must enforce |
| --- | --- | --- |
| Invoice type changes before first save | Item types, allowed taxes, recommended sales account, numbering rule, all lines | Item types and taxes belong to selected voucher type; immutable after draft creation. |
| Invoice date changes | Numbering rule, financial year, currency rate when date-effective rates are introduced | Date belongs to a financial year and falls within the selected prefix/suffix date range. |
| Customer changes | Contract, customer defaults, all contract-dependent vehicles and lines | Contract belongs to customer. |
| Contract changes | Vehicles, rental/fine/salik source-charge candidates, all lines containing an old vehicle | Contract required for Rental/Fine/Salik and selected vehicle belongs to contract. |
| Vehicle changes | Vehicle-specific description or future source charge detail | Vehicle exists; Vehicle Invoice requires it on every line. |
| Item type changes | Suggested tax and line description only | Item type is active and belongs to selected voucher type. |
| Tax changes | Line tax amount and tax summary | Tax is active and mapped to selected voucher type. |
| Exchange rate changes | Currency display | Exchange-rate ID exists; currency display derives from its currency. |

## Database Relationship Finding

The live database has **no declared foreign keys** among the reviewed Sales Invoice, lookup, contract, and contract-vehicle tables. Therefore MSSQL will not automatically delete, update, or protect related data when a referenced record changes.

The application must retain these safeguards:

- Draft update: replace `tbl_SalesDetails` and `tbl_SalesBillTax` inside one transaction.
- Draft delete: use `dbo.SalesInvoiceDelete`, which archives/deletes related invoice records.
- Post/unpost: do not enable until the VAT output-ledger, party-balance, source Fine/Salik, and Vehicle Sold-status reversal rules are confirmed.
- Every create/update: validate all supplied IDs against their lookup table and validate the business relationships listed above.

## API Work Still Needed

1. `GET /sales-invoices/lookups/numbering-rule?invoiceType=&invoiceDate=`: returns the valid `suffixPrefixId`, prefix/suffix, width, padding, and current policy; return a clear validation error for Vehicle until its no-rule policy is confirmed.
2. `GET /sales-invoices/lookups/contracts?customerId=`: return eligible contracts with ID, reference, date/status, and the customer relationship.
3. `GET /sales-invoices/lookups/vehicles?invoiceType=&contractId=`: return only contract vehicles for Rental/Fine/Salik; return sellable registered vehicles for Vehicle; support optional vehicle for Misc.
4. Improve `taxes` to require `invoiceType` and filter active `tbl_Tax` rows through `tbl_VoucherTypeTax`.
5. Improve `exchange-rates` to join `tbl_Currency` and return the human-readable currency data.
6. Replace broad `sales-accounts` with an approved per-invoice-type revenue-account configuration. The current table itself does not establish that mapping.
